# 全流程与阶段门禁

## 原则

流程用于减少错版、丢决定和无效返工，不要求已有项目补做全部步骤。先判断当前处于哪个阶段，只补当前交付真正缺失的证据。

```text
材料与当前版本
  → 产品事实 / 平台调性 / 未知项
  → 基础图形方向
  → 受控探索或局部编辑
  → 统一评审与人工确认
  → 呈现层校准
  → 小尺寸 / 手机主屏 / 背景组合
  → HTML / Figma 交接
  → 矢量与生产交付
```

## 证据层

| 类型 | 含义 | 不得冒充 |
|---|---|---|
| Source fact | PRD、业务方、明确素材或用户反馈中可定位的事实 | AI 推断 |
| AI judgment | 对语义、调性、风险和下一步的判断 | 人工确认 |
| Human decision | 设计师/业务方对具体版本和范围的决定 | 永久通用规则 |
| Generated artifact | 某次工具调用或程序生成的输出 | 已验收资产 |
| Mechanical validation | 路径、格式、尺寸、哈希、字段、节点数量通过 | 视觉通过 |
| Visual QA | 实际查看目标画面后的观察 | 最终业务批准 |
| Production-ready | 真正完成矢量、尺寸、用色、授权和交付要求 | 评审位图 |

## Stage 0 · Resume / Intake

新项目收集 PRD、名称、用户、关键场景、禁区、竞品、既有资产和交付要求。已有项目额外收集：

- 当前保留和搁置的版本；
- 最近一次人工确认；
- 不可变化的几何、位置、颜色或构图关系；
- 目标 HTML、Figma 文件和节点；
- 本轮只解决的问题。

产物：来源索引和 current truth。材料不全时，只询问会改变结果的缺口。

## Stage 1 · Product Grounding

按顺序回答：产品解决什么问题、用户何时使用、核心行为/关系、真正差异、主要使用位置、名称与文化限制。每个结论标注来源或 AI 假设。

产物：`01-brief.md`。

## Stage 2 · Direction Framing

方向以不同的核心隐喻或构形机制区分，不以颜色或材质区分。数量由任务决定；一个明确局部修改不需要强造三条方向。

每个方向说明：产品依据、基础图形、识别机制、正负形、优势、误读风险、禁区和主要场景。

门禁：事实无明显错误，方向差异真实，风险已说明，人工允许进入生成。

## Stage 3 · Controlled Exploration

每批只改变一个主要变量。保存输入、提示词、工具/模型、时间、参考角色、输出、哈希和观察。原始输出只增不改。

若用户已指定准确局部修改，跳过大规模发散，直接执行局部编辑并对禁改区域做差异检查。

## Stage 4 · Shape Review

先看单色基础关系：第一眼主体、轮廓、正负形、比例、连接/遮挡、24–64 px。硬问题不能靠材质得分补回来。

可以保留多个方向。`retained` 表示继续评审，不等于生产批准；`parked` 保留历史但退出当前页面。

## Stage 5 · Presentation Calibration

固定母形后再比较颜色、背景、材质和容器。一次修改一个变量；任何呈现层改变导致轮廓或语义关系丢失时退回母版。

## Stage 6 · Context Review

把所有当前方案放入要求的背景、尺寸和手机主屏。比较条件一致，但每个方案可有独立 `contain` / `full-bleed` 和光学尺寸。

## Stage 7 · Handoff

评审 HTML、确认快照、素材哈希和 Figma 使用同一 revision。写入指定文件/节点，回读数量、顺序、标题、图片与清晰度。

## Stage 8 · Production

用矢量工具重建最终路径；定义彩色、单色、反白、最小尺寸、安全区、App icon 专用版和字标关系。完成相似性/法律检查状态记录。

## 何时算完成

- 本轮要求的对象全部进入相同评审条件；
- 当前版本、背景组合和手机主屏没有漏项；
- 人工确认绑定到具体版本、配色和资产；
- Figma 实际写入并回读；
- 生产状态没有被评审稿冒充。
